## 一、总体结论

**成熟度评级：可用（Production-capable），但存在一个必须修的结构性缺陷。**

服务已经能稳定完成「采集 → 分析 → 聚类 → 评分 → 选槽 → 排版 → 推送 → 台账」全链路，工程化程度高于同类个人项目：有幂等导入、失败重试、熔断、保留策略、零成本回放调参、反馈闭环。277 个测试覆盖了主要契约，且多数测试锁的是**真实踩过的坑**（注释里带 BUG 编号），这是好实践。

但有一处结构性问题：**story 身份不稳定，导致孤儿记录累积**（详见 P0-1）。它不影响今天能跑，但会随运行天数线性恶化，且当前无清理机制。

评分：架构 **B**、可靠性 **B+**、可维护性 **C+**、需求覆盖 **B**。

## 三、问题清单

### P0-1　story 身份不稳定，孤儿记录持续累积

**现象**：同一 B 站视频（`BV14UsB6nE1D`）产生 4 条 story，其中 3 条无任何文档归属。

```
a9183ce79be2  32.4分  关联文档 0 个
8179f4b902c3  34.4分  关联文档 0 个
12d23b58c471  34.4分  关联文档 0 个
57c902ce53bc  32.4分  关联文档 2 个  [1859, 1891]
```

**根因**（`pipeline.py:216-251`）：

```python
chosen = str(story["id"])
if chosen in used:
    salt = len(used)                    # ← 非确定性
    chosen = story_id_for(f"{title}#{salt}", first_seen)
```

1. `salt = len(used)` 依赖本轮遍历顺序，同样输入换个顺序就得到不同 id；
2. 旧 story 不因「文档被新 story 接管」而删除，`story_docs` 也不清理；
3. 结果：每轮重跑都可能新增一条孤儿。

**影响**：
- 孤儿占 `stories` 的 **5.9%（14/237）**，污染报告页与 `history`；
- 孤儿 `status='scored'`，**满足 `backlog_candidates` 的过滤条件**（该 SQL 不 join `story_docs`）；
- 当前实测「符合 backlog 条件且无文档归属」为 **0 条**（分数都低于 45），所以是**潜在风险而非现行故障**——但一旦出现高分孤儿，就会被当成「历史好文」推出去。

**修复建议**：
1. salt 改为确定性来源：`hash(簇内最小 raw_doc_id)` 或直接取 `sha1(title|first_seen|sorted(member_ids))`；
2. `prune_orphan_stories()`：删除 `id NOT IN (SELECT DISTINCT story_id FROM story_docs)` 且 `first_seen` 早于 1 天的记录；
3. `backlog_candidates` 增加 `AND id IN (SELECT story_id FROM story_docs)`。

## 五、架构评估

### 分层与依赖

```
cli / runner                （编排）
   ├── adapters            （采集，依赖 httpclient/browser）
   ├── content             （正文抓取）
   ├── llm                 （分析）
   ├── pipeline            （聚类/评分/选槽）  ← 纯函数为主，可测性好
   ├── render→notify       （排版/推送）
   ├── pricing/price_sources（价格）
   ├── db                  （持久化）
   └── server/doctor/history/replay（旁路）
```

**优点**：
- `pipeline.py` 基本是纯函数（输入 stories、输出槽位），277 个测试里大部分直接测它，无需数据库或网络——这是整个项目最健康的部分。
- `db.py` 统一封装事务（`tx()`），没有散落的裸 SQL 写操作。
- 采集适配器有统一接口和 `passes_filters` 钩子。

**缺点**：
1. **`pricing.py` 边界缺失**（P1-2），是唯一的上帝模块。
2. **`runner.py` 编排逻辑偏厚**（479 行），里面混了推送批次记录、价格刷新、报告生成；改动任一步都要读懂全文件。
3. **无依赖注入**：抓取、LLM、数据库都直接实例化，导致测试只能用 mock provider 而不能注入假抓取器。
4. **story 身份与标题耦合**（P0-1 的深层原因）：标题一旦被 LLM 改写或规范化规则变更，历史 id 就对不上，只能靠 `doc_to_story` 链条兜底——这条链一旦断（文档被清理），身份彻底丢失。

### 测试质量

- 277 个用例，10 秒跑完，无网络依赖 ✅
- 多数测试注释带 BUG 编号，能追溯到具体故障 ✅
- 但存在「测试死代码」现象（P1-4），以及部分测试用「改参数迎合实现」的方式修正（如 freshness 曲线）⚠️

### 收尾阶段补的两处

**① 孤儿保护期从 1 天收紧到 0。**

改完 salt 后仍会看到零星孤儿（实测 2 条），原因是：每次重跑若「分家」这类同标题被聚成不同的簇，被换下的旧 id 就成了孤儿。原来的 `keep_days=1` 要让它们等一天才清。

**② 定时任务其实从未触发过。**

`Get-ScheduledTaskInfo` 显示 `LastRunTime = 1999-11-30`、`LastTaskResult = 267011`（0x41303「任务尚未运行」）。原因是任务在 11-17 12:00 之后才创建，首次触发本就是 11-18 12:00——不是缺陷，但意味着**调度链路在正式启动前没有被真实执行验证过**。

已做的验证：
- 用任务同款解释器 `pythonw.exe` + 同工作目录跑 `run.py status`，正常输出（`run.py` 里对 `sys.stdout is None` 的重定向生效）

- 动作定义：`pythonw.exe` + `run.py run`，工作目录正确

唯一残留风险：`LogonType=Interactive`，需要用户处于登录状态。若 12:00 机器关机或用户注销，任务不会执行（开机后 `StartWhenAvailable` 会补跑）。
