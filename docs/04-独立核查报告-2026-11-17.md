### 1.2 七个架构级问题

**ARC-01 · 单体式巨型模块**
`pricing.py` 1056 行、`pipeline.py` 911 行、`render.py` 504 行、`db.py` 475 行。
`select_slots()` 198 行同时处理：时间窗过滤、破平排序、五级补位、商品槽、中文槽、多样性去重、backlog 衰减、备选池扩充。
`run_daily()` 256 行串起 8 个阶段。
→ 任何一处改动都要重读整段，回归风险高。建议按 `cluster.py / scoring.py / claims.py / slots.py`、`pricing/{import,summary,overseas}.py` 拆分。

**ARC-02 · 状态一致性靠"代码顺序"而不是事务**
渲染 → 判幂等 → 发送 → 写台账 → 清理，五个步骤各自独立提交。中间任何一步失败或进程被杀，都会留下不一致状态（已发布日报被覆盖、推送发了没记账、台账记了没发）。
→ 需要一次显式的"投递事务"：先占位（in-flight 行）→ 发送 → 置成功。

**ARC-03 · 增量式修复没有回填机制**
新增列（`publisher_domain`、`derived_tier`、`time_source`、`confidence`、`published_at`）只对**新入库**的行生效；存量行为 NULL，代码靠 `COALESCE` 兜底——但兜底值往往就是错的（`publisher_domain` 为空 → 退化成 `news.google.com`；`derived_tier` 为空 → 退化成查询源 tier）。
**实测：211 条 raw_docs 里只有 8 条有 publisher_domain。**
→ 要么写一次性回填脚本，要么让这些字段在缺失时走"未知"而不是"继承错误的默认值"。

**ARC-04 · 同一语义两套实现**
幂等：`already_pushed_slot`（死代码）与 `pushed_today`；
价格模型：`skus/price_snapshots`（死表）与 `products/price_points`；
周号：`cli._iso_week` 与 `pricing._iso_week` 各一份；
域名提取：`httpclient.url_host` 与 `pipeline.independent_sources` 各一份。

**ARC-05 · 校验层依赖"单一信号"**
可信度最终只由 `authenticity`（一个字母）表达，而它是 tier + 域名数 + 传闻词 + 矛盾的复合结果。任何一环失真（如 `publisher_domain` 缺失），整条链都失真，且下游无法察觉。

**ARC-06 · 测试结构失衡**
139 个用例里 128 个是纯函数测试；**没有一条**覆盖 `run_daily`、`prune_raw_docs`、`_record_pushes`、`server.do_POST`、适配器的 Playwright 路径。本轮找到的 1 个 P0 与 6 个 P1 全部落在盲区。
→ 至少补三条：① 全流程跑一次（临时库 + mock 推送）；② 保留清理；③ 纯价格日记账。

**ARC-07 · 文档再次漂移**
设计文档 §18/§19 是前两轮写的"已修复"清单，其中至少 4 处与当前代码不符（见 §5）。README 未提"纯价格日不记账"、"浏览器源时间失效"等已知行为。

## 2. P0 缺陷

### C-01 · 浏览器源取不到发布时间，旧闻按今日新闻计分

**【实测 · 已复核】**

`src/infotwitter/adapters/__init__.py:341-345` 的抽取脚本：

```js
const t = node.querySelector('time[datetime], [data-date], [datetime]');
if (t) { dt = t.getAttribute('datetime') || t.getAttribute('data-date') || ''; break; }
```

对 `https://www.warhammer-community.com/en-gb/all-news-and-features/news/` 的真实渲染结果（子审计执行）：

- 页面里 `<time>` 出现 20 次，`datetime=` 出现 **0** 次，`data-date` **0** 次
- 实际元素是 `<time class="copy-bitter-xs whitespace-nowrap">Mon 16 Nov 26</time>`——日期只在**文本**里
- 该 JS 对 20 个文章链接全部返回 `datetime=""` → 全部走 `_published_or_fetch("")` → `now_iso(), "fetch"`

生产库佐证：`whc_news` 的 20 条文档，`published_at == fetched_at` 的比例 **20/20**，且时间戳完全相同（`2026-11-17T14:50:27`）。

**这条路径在 `fetch()` 里还有一个独立问题**：函数签名接收 `since`，但循环体（`:350-376`）**从未使用它**——浏览器源没有任何时间过滤，抓到什么算什么。

**影响（正在发生）**：
- `Warhammer Age of Sigmar: October Update`（真实发布 2026-10-28，20 天前）当前得分 **60.7**，`freshness = 5.0`，排进当日 Top 5；它只因槽位被更高分占满才没被推送。
- 今天实际推送的槽 1/2/4 全部来自 `whc_news`，`published_at == first_seen_at == 14:50:27`——**推送里的"今日新闻"时效是伪造的**。
- 补丁 `time_source='fetch'` 只在 `pipeline.py:471-473` 把 freshness 上限压到 3.0（60.7 → 约 56.7），仍高于 55 分门槛；`published_cutoff` 用的也是被污染后的 `published_at`，拦不住。

**修复**：
```js
// 1) 退一步读 time 元素的文本
const t = node.querySelector('time');
if (t) { dt = t.getAttribute('datetime') || t.getAttribute('data-date') || (t.textContent||'').trim(); }
```
```python
# 2) Python 侧按常见格式解析文本日期（"Mon 16 Nov 26" / "16 Nov 2026" / "Nov 16, 2026"）
# 3) fetch() 里真正用 since 过滤；解析失败就丢弃该条，不要写入 now()
# 4) time_source='fetch' 的单源 story 直接排除出槽 1-4，而不是只扣 4 分
```

## 3. P1 缺陷

> 每条都给出可复现的证据；标「已复现」的是我在本机实际跑出来的。

### S-01 · 保留清理撞外键，第 14 天起每天失败（已复现）

`db.py` `prune_raw_docs()` 执行 `DELETE FROM raw_docs WHERE ... < cutoff`，而 `claims.raw_doc_id` 是 `REFERENCES raw_docs(id)` 且 `PRAGMA foreign_keys=ON`。

复现（临时库）：插入 1 条 30 天前的 raw_doc + 1 条引用它的 claim，调用 `prune_raw_docs(14)`：

```
!!! 失败: IntegrityError FOREIGN KEY constraint failed
prune 后 raw_docs: 1    prune 后 claims: 1
```

**影响链**：`run_daily` 第 7 步 → 异常 → `finish_run(status='error')` → 抛出 → 定时任务 `LastTaskResult != 0`。
`prune_content_cache()` 与 `db.vacuum()` 在这行之后，**永远不会执行**。
第一条文档入库于 2026-11-17，14 天后（约 12-01）开始每天失败。

**修复**（三选一，推荐前两个一起做）：
```sql
-- A. 建表时就声明级联（新库）
raw_doc_id INTEGER REFERENCES raw_docs(id) ON DELETE SET NULL
-- B. 清理前先解绑（存量库）
UPDATE claims SET raw_doc_id = NULL WHERE raw_doc_id IN (
    SELECT id FROM raw_docs WHERE COALESCE(published_at, fetched_at) < ?);
```
另加一条集成测试：`prune` 在有 claim 的库上必须不抛异常。

复现：

**影响**：同一个事件今天一个新 id、明天另一个 id。`pushed_story_ids` 按 id 去重 → **同一事件可被推两次**。

### S-02 · 增量修复没有回填，96% 的存量数据仍用错的层级（已复现）

```sql
SELECT COUNT(*) total, SUM(publisher_domain IS NOT NULL AND publisher_domain<>'') filled FROM raw_docs;
-- 211 / 8
```

只有本轮新采集的 8 条中文 Google News 有 `publisher_domain` / `derived_tier`；其余 203 条为 NULL。
下游 `independent_sources()` 回退到 `urlparse(url).netloc`，对 Google News 条目就是 `news.google.com`：

- 两个不同媒体（SpikeyBits / Wargamer）的报道被压成 1 个域名 → 真多源无法升级；
- 一条真实 RSS（goonhammer.com）+ 一条 gnews（news.google.com）→ 被判成 2 个独立域名 → **虚假升级**（BUG-03 的老形态，换了个入口）。

同理 `time_source` 全库都是 `'feed'`，浏览器源那 20 条本该是 `'fetch'`。

**修复**：写一次性回填（gnews 按标题后缀 ` - Source` 或 URL 反查 publisher；browser 源全量标 `fetch`），并在 `independent_sources` 里把 `news.google.com` 视为"不可用作独立信源"。

### D-01 · 纯价格日"发了但不记账"，同日会重复推送（已复现）

```python
has_content = any(slots.get(k) for k in ("general", "product", "cn", "product_rows"))  # 发送认 product_rows
...
if slots.get("product"):     # 写台账只认 product
    db.record_push({..., "slot": 5, ...})
```

隔离实验（未来日期，避免历史行干扰）：

```

pushed_today = False
→ 纯价格日发了却不记账，同日会重复推
```

**触发条件很宽**：`product_rows` 几乎每天都有 5 行（1745 个商品），只要当天 `general/product/cn` 都为空（安静的周末），就会命中。

### D-02 · 渲染发生在幂等判定之前，已推送日重跑会覆盖已发布日报

代码顺序：`build_report()`（写 `{date}.html` + `latest.html`）在第 196 行，`pushed_today` 判定在第 233 行。
现场证据：台账 payload 全是 3941 B、发送时间 16:32；磁盘 `push-2026-11-17.html` 是 5395 B、mtime 16:50 —— 16:50 有一次运行把"发布物"改了却没发新推送。

**影响**：用户点开 16:32 收到的链接，看到的是 16:50 重算的另一份日报。

### D-03 · 发送与台账之间没有原子性，也没有跨进程互斥

`_send_with_retry` 成功后才调 `_record_pushes`，后者每个槽一次独立事务。送达后进程被杀 → 台账 0 行或半行 → 下次重推。
两个 `run` 进程（手工 + 计划任务）都读到 `pushed_today=False` 就会都发——`IgnoreNew` 只防同一任务重叠。

### D-04 · 反馈令牌按"页面生成日"校验，次日 12 点前全部 403（已复现）

```python
today = datetime.now(CST).date().isoformat()
if not verify_feedback_token(today, token): return 403
```

实测：今天的 token → 200；昨天的 token → 403。
日报是 12:00 生成的静态页 → **次日 00:00–12:00 之间（约 12 小时）所有按钮都失效**，而提示写"请刷新日报页"，对静态文件无意义；回看历史日报也永远无法反馈。

**修复**：服务端接受 D 与 D-1，或令牌内嵌生成时间给 48h TTL。

### D-05 · 反馈请求每次重建数据库，锁竞争时直接 500

`record_feedback()` 每次 `Database(db_path)` → `executescript(schema.sql)` + `_migrate()`（含一次 `UPDATE raw_docs ...`）。
子审计实测：另一连接持写锁时，POST 在 **5474 ms** 后返回 `500 {"ok":false,"error":"internal"}`，日志 `sqlite3.OperationalError: database is locked`。
我另测初始化本身约 **5 ms**——不是性能问题，是**正确性问题**：日报写入或 VACUUM 期间用户的点击会丢。

**修复**：请求路径用只读连接、不做 DDL/迁移；`PRAGMA busy_timeout=3000` + 一次重试。

### D-06 · 令牌的盐在 import 期固化，`.env` 里的 `INFOTWITTER_FEEDBACK_SALT` 无效

`tokens.py` 在导入时读 `os.environ`，而 `load_dotenv()` 在 `load_config()` 里才执行，导入链更早。实测 import 后改环境变量，token 不变。

### P-02 · `confidence=low` 只在"最佳价"过滤，最低价/涨跌/置信列都没过滤

```python

lowest = min(domestic, ...)
```

实测（线上 01-10 图拉真）：一条 `confidence=low`、样本 1 条、note 写着"材质你懂的"的 ¥50 闲鱼帖，被展示为 **"最低 ¥50 闲鱼"**，同行"置信"列显示 **high**（取的是官店价的置信度）。

### P-03 · 海外价匹配守卫可绕过

守卫整体包在 `if matched and target_name:` 内 → 不传 `matched` 直接放行；`EDITION_TOKENS` 没有 jp/japanese；`_category_family` 把 codex/book/boxed 一律归为 `mini`。
实测：`matched="Adeptus Custodes Custodian Guard (Japanese)"` 对英文版商品 → `saved=1, confidence=high`。

### P-04 · CLI 匹配阈值 0.55 太松，且首个达标就 break

`--min-score` 默认 **0.55**（函数默认 0.7）。实测 `ADEPTUS CUSTODES: CUSTODIAN GUARD` vs `... CUSTODIAN WARDENS` = **0.60** → 兄弟商品通过；而正确匹配 `... with Adrasite Spears` = 0.29 被拒。
`if best_score >= min_score: break` 让更精确的尾部查询失去机会。

### P-05 · `observed_at` 是自由字符串，唯一键形同虚设

三处入口都写日期，但 `--observed-at` 原样透传不校验。实测同一文件按 `2026-11-17` 与 `2026-11-17T09:00:00+08:00` 各导一次 → **4 行**（本该 2 行），`price_movements` 立刻算出 **+20%** 假涨跌；`2026/11/17` 这种格式还能让 `date.fromisoformat` 在 CLI 里直接抛异常。

### P-06 · Excel 导入静默丢价

- `if len(r) > 8:` → 8 列（无 New 列）的调价表得到 `price_points: 0`，退出码仍 0；
- New 两列都空的行不写价格点，商品却照常 upsert；
- 合并单元格的续行 `r[0]` 为 None → 丢内包装编码；
- 数字格式货号（`9901`）没有 `-` → 整行跳过。

### C-02 · `bilibili.py` 的 f-string 含反斜杠，Python ≤3.11 直接 SyntaxError

```python
key = f"{re.sub(r'\s+', ' ', (title or '').strip().lower())}|{url.strip().lower()}"
```

`requirements.txt` 声明 3.11+，而 PEP 701 之前 f-string 表达式内不允许反斜杠。子审计用 3.10 实测：`SyntaxError: f-string expression part cannot include a backslash`。
当前机器是 3.12 所以能跑；**换到 3.11 部署，整个 `adapters` 包导入失败，采集全灭**。
（这行是我上一轮修 `_hash` 正则时引入的。）

### D-08 / D-09 / D-10 · 失败可见性的三个洞

- **D-08**：PushPlus token 分支永远返回 `WARN`，退出码 0 —— token 填错/欠费/`dry_run=true` 都判"健康"。这个项目唯一的目标就是"每天收到日报"。
- **D-09**：没配通道时 `ConsoleNotifier.send` 返回 `True`，`cmd_run` 返回 0，任务面板显示成功。
- **D-10**：只有**推送**失败写 `logs/alert.log`；采集全挂、LLM 欠费、模板异常的 `except` 分支不写。

### D-11 · `--force` 失败会把当天已成功的台账改成"未送达"

```sql
ON CONFLICT(push_date, slot) DO UPDATE SET ... delivery_ok=excluded.delivery_ok
```

12:00 成功（1），18:00 `--force` 失败（0）→ 全天 6 行被改成 0 → `history` 显示未送达、`pushed_today` 变 False → 再跑又发一遍。

### D-12 · 已注册的定时任务与安装脚本不一致

实机 `Get-ScheduledTask`：`Execute = ...\python.exe`（脚本要 pythonw）、`RestartCount=0`（脚本写 3）、`LogonType=Interactive`（脚本优先 S4U）。
→ 每天 12:00 弹黑框；失败不重启；且 `-Execute` 是 venv 绝对路径，项目一搬家任务立即失效而 doctor 仍绿灯。

## 9. A-06 + A-03 执行记录（2026-11-17 20:30–20:40）

**根因**：以前没有「事件身份」，`story_id` 是每次聚类时按"簇里最早那篇的标题+日期"**临时算**出来的。
簇成员一变（合并进更早的一篇），id 就变；旧 id 的行留在库里没人管，就成了孤儿。

**做法**：引入一条**文档归属链** `story_docs(raw_doc_id → story_id)`，让事件身份从"每次重算"变成"沿链继承"。

### 9.1 A-06 · story_id 稳定

- 新增表 `story_docs`，每轮把该事件的所有文档重新挂到它的 `story_id` 上；
- 聚类后调用新的 `assign_stable_ids()`：一个簇若含历史上属于某 story 的文档，就**沿用那个 id**；
  多个候选时按 `first_seen_at` 取最老的（合并时老事件胜出）；
- 拆分场景特殊处理：两个簇抢同一个旧 id 时，先到的占用，后来的重新生成，避免主键冲突；
- 没有任何历史归属的簇，仍用原来按标题算出来的 id（首次出现时）。

**实测（连跑两轮，同一批数据）**：

```
运行前：库内 149 个事件，归属链接 0 条
第 1 轮：139 个事件，归属链接 211 条 / 139 个事件，新增 id 1 个
第 2 轮：139 个事件，归属链接 211 条 / 139 个事件，新增 id 0 个   ← id 不再漂移
第 1→2 轮相同 id：150 / 150
```

### 9.2 A-03 · 孤儿回收

- 新增 `expire_absent_stories(seen_ids, grace_hours)`：本轮没产出的事件标记为 `expired`，
  于是被 `backlog_candidates`（只认 `scored/skipped`）自动排除；
- **两条判定，满足其一即回收**：
  1. 它已经没有任何挂靠文档（每篇都被别的事件收走 = 被合并了）→ 立即回收，不必等宽限期；
  2. 超过宽限期（默认 24h）→ 兜住"某次源故障导致本轮没产出"的情况；
- 三道保险：`seen_ids` 为空时**绝不清理**（采集全挂的典型形态）；`pushed` 不清；宽限期可配；
- **复活路径**：`insert_story` 的 upsert 把 `status` 规则改成
  「`pushed` 保持，其余按本轮结果」——被回收的事件下次再出现会自动变回 `scored`，不会永久失活。

**实测（生产库副本 + 生产库）**：

```
库内 150 个事件，本轮产出 139，孤儿 11
宽限期 24h：回收 11（因为它们都没有挂靠文档了）
回收后：scored 139 / expired 11
backlog 候选 22 条，其中孤儿 0 条   ← 修复前是「模拟空窗日 2 条孤儿上桌」
复活路径：expired → scored ✅
```

生产库已按此执行一次定向回收（不重写任何已发布产物）。

### 9.3 副作用：日报现在是「无内容」

孤儿清干净之后，今天 dry-run 的结果是：

```
=== 选槽：mode=empty 通用=0 商品=1 中文=有 ===
推送：战锤日报 · 11-17 无内容 / ⑤ 模型价格速览 / ⑥ 中文社区
```

原因不是流程坏了，是**诚实之后确实没有合格内容**。48 小时内的事件有 102 个，但：

```
≥55 分: 1 条（就是 16:32 已经推过的那条 → 被台账排除）
≥52 分: 3 条
≥50 分: 5 条
≥45 分: 10 条
```

`qualified_score: 55` 这个阈值是在**时效被伪造的时期**校准的——当时 20 篇 whc 文章都以 `freshness=5.0` 计分，
Top6 能到 79/74/71。现在同一批内容拿到的是 `freshness=2.5`（44 小时前发布），分数整体下移 5–8 分。

**我的判断**：现在**不应该**立刻下调阈值。理由：

1. 今天的数据是"半路修正"的产物——库里还混着被修复过的历史行；
2. 明天 12:00 采集到的 whc 文章会是**当天发布**的（`freshness=5.0`），同样内容的分数会比今天高 3–5 分；
3. 至少要跑 2–3 个完整日更，看真实的"每天有多少条 ≥55"，才知道阈值该定在哪。

**建议**：观察 2–3 天。如果每天 ≥55 的条数稳定在 0–1，再把 `qualified_score` 按实测分布下调到 50–52，
并在 `config.yaml` 里写清校准依据（就像原来那条注释一样）。现在就调属于"用权重掩盖输入问题"。
