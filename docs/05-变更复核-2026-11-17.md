## 3. P1

### N-01 · 推送台账被清空，明天会把今天推过的再推一遍

**现状**：`pushes` 表 **0 行**；`data/backup/pushes-before-official.json` 里有 16:32 那次推送的 **6 条**完整记录（含 `delivery_ok=1`）。

**实测**（按当前台账跑一次选槽）：

```
场景 A 台账为空（现状）：
  1.  56.6 [qualified] 在 Grymmpeaks 开辟你的 Path to Glory
  2.  44.4 [aged]      周日预览：全新 Battleforce 套装集结待发
  3.  43.8 [aged]      兽人战团包：装甲闪击团

今天 16:32 已推的 6 个 story_id 里，有 1 条（341ef0425eefa5fb = Grymmpeaks）
会在明天被当成新内容再推一次。
```

**为什么这次特别危险**：`A-06` 让 `story_id` 变稳定了，所以"今天推的"和"明天候选的"能对上号——但台账是空的，`pushed_ids` 是空集，对上了也没用。

**修复**（二选一，建议第一个）：

```powershell
# 把备份导回台账（字段完全对得上）
python -c "import sqlite3,json;d=json.load(open(r'data/backup/pushes-before-official.json',encoding='utf-8'));c=sqlite3.connect(r'data/infotwitter.db');[c.execute('INSERT OR IGNORE INTO pushes (id,push_date,slot,story_id,sku_ids,title,importance,channel,payload,sent_at,delivery_ok) VALUES (?,?,?,?,?,?,?,?,?,?,?)',tuple(r[k] for k in ('id','push_date','slot','story_id','sku_ids','title','importance','channel','payload','sent_at','delivery_ok'))) for r in d];c.commit();print('恢复',len(d),'条')"
```

或者，如果清空是刻意的：至少把这 6 个 `story_id` 写进一个 blocklist 交给 `select_slots`，否则"新窗口第一次正式跑"就会重复。

### N-02 · 跨天同标题去重实际不生效

设计把 `dedupe_same_title()` 写成"防止前一天推过其中一条、另一条第二天被当新内容再推"的措施。但执行顺序是：

```python
for s in stories:
    if s["id"] in pushed_ids:   # ← 被推过的那条在这里就被剔除了
        continue
...
fresh = dedupe_same_title(fresh)   # ← 去重在这里，已经看不到它了
```

**合成复现**（同标题两条，id 不同，昨天推了其中一条）：

```
昨日已推 pushed_yesterday，今日候选里还剩 today_dup
选中: ['today_dup']
→ ❌ 同一事件被再推一次
```

**修复**：把去重前移到 `runner` 聚类之后——同标题的簇合并成一个 `story_id`，并把两簇的成员文档都挂到存活 id 上（`link_story_docs`），被并掉的那条自然无挂靠文档，被 `A-03` 立即回收。这样 `select_slots` 里就不用再猜了。

### N-03 · 报告页和推送显示两个不同的分数

同一条「周日预览」，推送里是 **44.7分 · 本周稍早**，报告页里是 **67.0 分 · 本周稍早**。

原因：`_shown_score()` 只改到了 `render.py` 的推送路径，`templates/report.html.j2:90` 仍用 `{{ item.importance_total }}`。
台账 `pushes.importance` 记的也是原始分（`_record_pushes` 用 `importance_total`），所以 `history` 里看到的又是第三个数。

设计 §17.25 把"展示分与排序分一致"列为已修问题——**只修了一半**。

**修复**：`build_report` 里把 `_decayed` 透传到模板上下文，模板用 `_shown_score` 等价物；台账也记展示分（或同时记 `score_raw` 和 `score_shown`）。

## 4. P2

### N-04 · `windows.cn_slot_days` 在 config 里定义了两次

```yaml
  cn_slot_days: 3        # L34
  ...
  cn_slot_days: 7        # L37
```

PyYAML 不报错、静默取后者 → **实际生效 7 天**。而设计 §17.25 第 5 条明确写"槽 6 仍用 `cn_slot_days`（3 天）……否则中文源会被大量老内容淹没"。

实测：`cfg.cn_slot_days == 7`。所以槽 6 的窗口不知不觉从 3 天放到了 7 天，正好是设计想避免的那件事。

### N-05 · aged 的门槛看原始分，展示看衰减分，中间没有下限

```python
if score < aged_min:            # 原始分 ≥ 50
    continue
decayed = score * (0.92 ** age_days)   # 展示的是这个
```

实测：一条 6.6 天前、原始 **55** 分的事件 → 衰减 **31.8** 分，仍然入选并以「31.8分 · 本周稍早」推送。
而 `backlog_min_score` 是 **45**——一条 31.8 分的内容走 aged 通道进去了，走 backlog 通道进不去。

**建议**：要么把门槛压在衰减分上（`decayed >= aged_min`），要么给展示分加一条硬底线（不低于 `backlog_min_score`）。

### N-06 · `backlog_days` 与采集窗口完全重合，降级阶梯少一级

`backlog_days: 7`，`collect_hours: 168h = 7 天`。二级 `aged` 先跑，`backlog` 只能在 aged 也凑不满时补位——而它俩的范围是同一个区间（只是过滤条件不同）。实测今天的选槽 `mode=aged_fill`，backlog 一次没进。

不致命，但设计 §8.4 画的五级阶梯实际只剩四级，`backlog` 的"历史推荐"标签近乎失效。

### N-07 · 去重键优先用译名

```python
raw = story.get("title_zh") or story.get("canonical_title") or ""
```

设计 §17.4 自己写过「story_id **不得依赖译名**，LLM 换个译法 ID 就变」。去重键犯了同一个毛病：译名一变，"同一事件"就认不出来了，标题相同的两条又会同时出现。

**建议**：去重键用 `canonical_title`（原文），译名只用于展示。
