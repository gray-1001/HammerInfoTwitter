## 2. P0

### P0-1 浏览器源抓到的发布日期是错的（4/6 实测）

**位置**：`src/infotwitter/adapters/__init__.py:410-427`（JS 祖先 `querySelector`）

```js
for (let d = 0; node && d < 6; d++, node = node.parentElement) {
    const t = node.querySelector('time, [datetime], [data-date]');   // ← 搜整棵子树
    ...
}
```

对每一级祖先做 `querySelector`，会在**祖先容器的所有后代**里找第一个 `<time>`。锚点位于侧栏"最多阅读"区时，
命中的是别的卡片的日期。

**实测**（2026-11-18 11:41，真实站点 + 真实代理）：把列表页抽到的日期与文章页 JSON-LD `datePublished` 逐条对照：

```
✅ 列表=2026-11-16  文章页=2026-11-16  Forge your Path to Glory in the Grymmpeaks
❌ 列表=2026-11-17  文章页=2026-11-15  Sunday Preview – The legions of Khemri arise
❌ 列表=2026-11-17  文章页=2026-11-11  New Core Mission Pack for Warhammer: The Horus Heresy
❌ 列表=2026-11-17  文章页=2026-11-14  Saturday Pre-order – Grab your Battleforce boxes
❌ 列表=2026-11-17  文章页=2026-11-12  The Adepta Sororitas make their presence known
✅ 列表=2026-11-17  文章页=2026-11-17  The Destroyer curse hits Loremasters on Warhammer TV

6 条里 4 条不一致
```

**影响链**：`since` 窗口过滤失效（本该 20 天前被排除的文章被判成今天）→ 时效分虚高 → "今日新闻"判断失真
→ 一级/二级分层错 → 最终推给读者的"今日"是假的。

**修复方向**（二选一，建议同时做）：
1. 日期只在**锚点自己所属的卡片**内取：`e.closest('[data-card], article, li')` 且校验 `t.closest('a') === e`；取不到就判未知。
2. 兜底：该源本来就是 `deep_fetch: true`，`content.enrich_docs` 会逐篇打开文章页——在那里读 JSON-LD `datePublished` 回写 `raw_docs.published_at`（零额外成本）。

### P1-2 一级/二级窗口用 `published_at`，与设计相反

`pipeline.py:946`：`ref = pub or dt`，然后 `if ref >= cutoff: fresh`。
而设计 §20 写的是"一级 = 首次出现 ≤48h"，§8.2 的推送窗口也是 `discovered_at`。

**后果**（合成实测）：

```
published=72h前 / first_seen=1h前  → fresh=0, aged=1, _decayed=70.1   ← 晚发现的真新闻被降级衰减
first_seen=100h前 / published=1h前 → fresh=1, reason=qualified         ← 早发现的更新反算一级
```

与 P0-1 叠加时更糟：日期是错的，分层就全错。

### P1-3 迟到的新闻永远进不了分析窗口

`db.py` 的 `recent_raw_docs` 按 `COALESCE(published_at, fetched_at) >= since` 过滤：

```
插入 published=2026-10-29 / discovered=2026-11-18 的文档：

  pending_analysis:        False
  prune_raw_docs(14):      立即删除 1 条
```

即"刚抓到但文章本身较早"的新闻，**既不会被分析，也会在 14 天后被直接删掉**。`discovered_at` 这个设计字段在这里落空。
