# 降噪与分析限额实施记录（2026-11-18）

> 范围：C-21（B 站降噪）、C-22（标题型文档只部分送 LLM）
> 测试：358 → **365** 全绿

---

## 1. 为什么这么改

今天的数据摆在这里：

```
reddit 157 + bilibili 109 = 266 条，占 352 条分析量的 76%
→ 13 条 ≥55 分里只出 1 条（Cherokee Open 门票）
→ 约 20 万 token/天几乎打水漂
```

而 B 站这类内容**没法靠加深补救**：视频简介实测只有 1–279 字（中位数几十），
播放量中位 58–571、最高不到 4 千——绝对阈值会把内容全杀掉。

---

## 2. C-21 B 站按播放量取前 N

新增 `top_n: 8`（4 个 B 站源），在时间窗过滤之后按播放量取前 8 条，再按发布时间倒序返回。

实测：

```
bilibili_wh     8 条  播放量 [1769, 781, 474, 452, 273, 171, 163, 109]
bilibili_40k    8 条  播放量 [837, 781, 474, 452, 273, 171, 163, 109]
bilibili_model  8 条  播放量 [3894, 1624, 1542, 1276, 1187, 792, 626, 573]
bilibili_paint  8 条  播放量 [3894, 1624, 1276, 862, 823, 441, 383, 178]

合计 32 条（改前每天约 109 条，降 71%）
```

## 3. C-22 标题型文档只部分成事件、送 LLM

新增两个配置：

```yaml
analysis:
  title_only_per_source: 12   # 每个源最多分析多少条「只有标题」的文档
  min_body: 400               # 正文达到这个长度就不受限
```

`db.limit_title_only_docs()` 在**进入流水线之前**过滤：

- 正文 ≥400 字的文档**不受限**（有真内容，值得花 token）
- 标题型文档按源保留最新的 N 条，其余**既不分析、也不参与聚类**——所以它们不会变成事件

这意味着 `stories` 数量会明显下降（今天 458 → 预计 250 左右），但留下的是有内容支撑的。

### 预计效果

| 源 | 今天 | 限额后 |
|---|---|---|
| bilibili（4 源） | 109 | 32（top_n 8 × 4） |
| reddit（5 源） | 157 | ≤60（每源 12） |
| tieba | 32 | 32（不超限） |
| googlenews | 32 | 32（不超限） |
| 其他 | 22 | 22 |
| **合计** | **352** | **约 178** |

分析量降约 **50%**，token 从约 28 万降到约 21 万/天。

## 4. 与 C-20（补抓按分数优先）的配合

三件事叠起来的顺序是：

1. **先补抓**：按事件分数优先，把 69.8 / 68.4 这类高分但没正文的条目补上（实测 12 条救回 4 条，96→1213、73→2795）
2. **再限额**：正文够长的直接进分析，标题型的按源取前 12
3. **最后降噪**：B 站只留播放量前 8

这样"补到的正文"不会被限额挡掉，而"没补到的"也不会无限吃预算。
