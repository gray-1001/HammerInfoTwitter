## 4. 架构评估

### 4.1 结构

```
collect(cfg, db)                  ← 46 源顺序遍历，契约 fetch(source, since) -> list | None
  ├── RssAdapter        ─┐
  ├── GoogleNewsAdapter ─┤ 走 Fetcher：熔断 / 限速 / 重试 / 代理降级
  ├── BrowserAdapter    ─┤
  ├── BilibiliAdapter   ─┘
  ├── TiebaAdapter      ─┐
  ├── NgaAdapter        ─┤ 自建 httpx / aiotieba / playwright，不共享任何治理
  └── RedditAdapter     ─┘

content: HTTP 优先 → 浏览器兜底 → trafilatura → 正文质量闸（≥250 字 + 2 个句末标点）
         + JSON-LD 日期回填 + 内容缓存 + 补抓
```

### 4.2 判断

**做得对的**：

1. **契约统一**：7 类适配器都是 `fetch(source, since) -> list | None`，`None=失败 / []=正常无内容`，这个区分很关键，collect 里没有一处要写特判。
2. **两段式正文抓取**：HTTP 先行，失败才起浏览器，实测 9 篇里 HTTP 拿下 2 篇、浏览器 2 篇，省掉大部分浏览器开销。
3. **正文质量闸**：`MIN_CHARS=250` + 至少两个句末标点（含 `。！？`），注释里写清了为什么从 400 降到 250——这是被真实数据校准过的参数。
4. **新增可观测性**：`source_stats` 表 + `run.py sources`，第一次能回答"这个源这周产出多少"。

**结构性问题**：

1. **两类适配器、两套治理**。reddit/tieba/nga 完全绕开 `Fetcher`，于是同一个域名被红迪 5 个源连打 5 次也不会有熔断；代理降级（socks 缺依赖时 `Fetcher` 会退直连）对它们不生效。
2. **采集层没有"预算"概念**。正文抓取有 `deadline_sec`，采集没有；46 源串行，最坏情况没有任何上限。
3. **"标题型源"没有对应的下游策略**。适配器老老实实采回标题，pipeline 老老实实花钱分析，中间缺一道"这条值不值得分析"的判断。

## 5. 需要决定的三件事

### 5.1 标题型文档要不要再花 LLM 分析？

三个选项：

- **A. 预筛**：只有标题命中「新闻性关键词 + 战锤实体」的才送分析（如 公布/发售/规则/更新/leak/announce）。
  代价：漏掉措辞不典型的帖子；收益：省掉大部分 token。
- **B. 只做信号不做内容**：红迪/贴吧/NGA 的文档只参与"传播热度/多源印证"，不单独成事件、不送 LLM。
  代价：中国社区槽可能缺料；收益：最省，且这些源的定位本来就是"社区温度"。
- **C. 保持现状**：全部分析，接受每天 27 万 token 换 1 条。

我倾向 **A**：给标题型文档加一道轻量预筛，命中才分析；不命中只入库用于热度。这样既保留"社区有讨论"的信号，又不让它变成 LLM 预算的黑洞。

### 5.2 补抓要不要按"能不能抓到"分层？

现状是 184 条候选、3/4 抓不到、每天重试 20 条。

建议：给 `raw_docs` 加一个 `fetch_fail_count`，连续失败 2 次的在 30 天内不再重试；或者把补抓范围从"所有 deep 源"收窄到"命中关键词的条目"。

### 5.3 长尾 0 产出源要不要下线？

46 源里 `gcores`、`yystv`、`yt_40ktheories`、`yt_squato` 等长期 0 条。建议按 `source_stats` 统计，连续 14 天 0 产出的自动降为 inactive（保留配置与历史）。
