## 一、结论

**流水线本身是稳的，内容正确性没有防线。**

能稳定跑完的：46 个源采集、LLM 分析、聚类评分、槽位分配、渲染、推送、台账、日报页、两个定时任务、价格全链路（翻译 1745/1745、货号匹配 1530/1530 一致）。365 个测试全绿。

但「推出去的东西对不对」缺少约束，四个地方会实际出错：

1. **聚类把无关内容并成一条**——实测一个 20 篇的簇（Old World 子版的各种闲聊帖）两两标题相似度均值 **0.029**，177/190 对低于 0.1；另一个 64.6 分的簇把「战团包预售」和「Dawn of War IV 预告」并在一起。
2. **日期拿不到时用抓取时间顶替**，且 `time_source` 落成 `feed` 绕过守卫——路径存在，31 个源暴露，目前数据未触发。
3. **槽 5 轮换是保序加法**——连续 7 天 top5 完全相同（实测），几十个已采价商品永远不露面。
4. **正文抓取大面积失败但日志显示「完成」**——904 篇里 708 篇正文不足 200 字，LLM 多数时候只看得到标题。

价格数据层反而是最扎实的部分：1530 条匹配全部货号一致、0 错配，时间格式 904/904 统一。

| 能力域 | 完成度 | 准确性 | 结论 |
|---|---|---|---|
| 采集（46 源 / 7 适配器） | 高 | 中（跨源重复 30.1%） | 能跑，输入质量被高估 |
| 内容抓取 | 中 | 中低 | 机制在，边界处理不足 |
| 分析/聚类/评分 | 高 | **低**（假合并、不可复现） | 最需要整改 |
| 选槽/展示 | 中 | **低**（轮换失效） | 看上去在工作 |
| 推送/台账 | 高 | 中（在途状态会卡死） | 可靠性有，恢复路径缺 |
| 价格模块 | 高 | 高（匹配 100%） | 数据对，分层要修 |
| 工程/运维 | 中 | 低（无版本控制） | 可运行，不可维护 |

## 二、三条 P0（都已复现）

### F-01 聚类假合并：内容会被并成一条错误的推送

位置：`pipeline.py:42`（`MIN_SHARED_ENTITIES=2`）、`:246-266`（并查集 union）、`:32-40`（黑名单）

规则是「两篇各含 2 个具体实体就合并」，且没有簇内聚度校验，A-B、B-C 会把 A/C 并一起。黑名单只列了 `reddit r/warhammer40k`，漏了 `warhammer fantasy`、系列名、媒体名。

实测（生产库 568 条 story）：

```
簇 9e72c869（22.4 分，20 篇）：Tilea 狮子涂装、TTRPG 版本提问、
  Averlion 女兵、Osterwald 战役…… 平均 Jaccard 0.029，177/190 对 < 0.1
簇 375167dd（64.6 分，17 篇）：「战团包预售」与「Dawn of War IV 预告」并成一条
  平均 0.150，96/136 对 < 0.1
```

`tests/test_clustering_regression.py` 自己写着上一轮同类事故吞掉了 79.4 分的新闻——**同一类问题第二次发生**，上次的修复只是补黑名单。

后果：内容静默丢失，高分故事的标题与实际内容不符。今天这次 64.6 分那条因为「发布超过一周」被丢弃才没推出去（见 A-02），属于运气。

### F-02 日期兜底成「抓取时间」，绕过旧文守卫

位置：`adapters/__init__.py:79-88`（`to_iso` 兜底 `datetime.now`）、`:221-223`、`:285-287`；守卫在 `pipeline.py:1019`

RSS / Google News 适配器**不写 `time_source`**，DB 默认填 `'feed'`；而守卫只拦 `time_source == 'fetch'` 且 `published_at` 为空。于是「feed 没给日期 → 用 now 顶替 → 标成 feed」这条路完全绕过守卫，旧文能以 24h 内新文身份进池并拿满分时效。

审计用合成 feed 复现：21 天前的条目入库后 `published_at=now`、`published - since = 21 天`、`time_source='feed'`。

当前生产库未触发（`published_at == discovered_at` 的 0 条；19 条「<2 分钟」全是 B 站真实新视频）。**属代码路径风险，不是现存脏数据**——但影响 16 个 RSS + 15 个 GNews 源。

### F-03 槽 5 假轮换：7 天 top5 一模一样

位置：`pricing/summary.py:65-67`：`ABS(rowid * 2654435761 + seed) % 100003`

`seed` 每天 +1，等于给所有排序键同时加 1，取模后只是循环移位，**顺序不变**；只有跨过 100003 边界才换 1 项，按当前商品数约 43 天一换。

实测（真实 2332 个商品）：

```
seed 20261113…20261119 连续 7 天：
['01-08','01-11','83-88','99120117019','99120599015']  ← 七天完全相同
```

后果：价格栏每天同样几行，1500 多个有海外价的商品里绝大多数永远不曝光，「每日速览」的产品目的落空。

## 三、分域问题（P1 精选，完整见清单）

### 采集

- **NGA 拿最后回复时间当发布时间**（`nga.py:144-175`）：审计用「700 天前老帖、2 小时前被回复」复现，结果 `published_at=今天` + `time_source=article`。老帖被顶起即成今日头条，且自带可信标记。
- **Reddit 的 filter / min_gap 全部失效**（`reddit.py:130-161`）：库内 275 行 reddit 里有 39 条标题以 `?` 结尾、60 条不足 24 字，配置里的 `reject_suffix` / `min_title_len` 从未生效。
- **跨源重复 30.1%**（实测 272/904 行）：唯一键是 `(source_id, content_hash)`，跨源永不撞键；bilibili 四个关键词源共用同一批视频，最多 4 源同一条 URL。
- **正文抓取静默失败**（`content.py:185-379`）：单 URL 失败只写 debug，成功数 15/30、25/71 照常打印「完成」。904 篇里 708 篇正文 <200 字。
- **429 反而升级到浏览器兜底**：被限流的站点会再挨一次更重的请求。

### 分析 / 评分

- **阈值断崖**（`pipeline.py:1051-1150`）：今日 48h 池 518 条，≥55 分只有 4 条；把这 4 条标记为已推后重跑，直接 `mode=empty`。没有 50–55 的次级档。
- **文章龄死区**（`pipeline.py:1024-1028`）：按 `published_at` 判「超一周」就丢，而 `first_seen_at` 才是发现时间。实测当日最高分 69.0 / 68.4 / 64.6 三条被静默丢弃，且因为仍在 `current_ids` 里，backlog 也永远捞不到。日志 Top5 还照样把它们印出来，运维会误判。
- **评分不可复现**（`pipeline.py:344,348-359`）：同一批数据换输入顺序，15/564 分数变化（如 54.4↔32.6），`canonical_title` 也会变。原因：同一秒并列时排序退化为输入序，`picked` 取「第一个非 fallback 分析」。
- **预算名不副实**（`llm.py:110-143`、`runner.py:136`）：`daily_token_budget` 实际是「每次运行」预算，每次新建 client 从 0 计数。实测 11-17 共 16 次运行累计 **1,133,274 tokens = 名义日预算的 142%**。真耗尽时静默降级，无告警。

### 推送 / 台账

- **在途状态会卡死**（`runner.py:431-437`、`db.py:647-682`）：先写 `delivery_ok=2` 再发送；进程被杀则永远是 2，下次 `pending_today` 直接返回 `already_pushed`，`runs.status=ok`、退出码 0、无告警。当天静默不推。
- **`--force` 重推被自己挡回**：`begin_push_batch` 的 `WHERE delivery_ok<>1` 让重推更新 0 行，但 `_publish_report` 已经把 `latest.html` 换成了新页——台账、站点、读者实收三处不一致。
- **先发布后发送**（`runner.py:372-386`）：渲染直接写站点根目录，发送失败/无内容/console 降级都会先覆盖 `latest.html`。实测现在站点根只有 `latest.html`（11-18 内容），日期页 `/2026-11-18.html` 404。
- **定时任务是 Interactive**：S4U 注册失败后静默退回，实测两个任务 `LogonType=Interactive`——注销就不执行，而面板仍显示 Ready。
- **1h 超时 vs 2h 锁**：任务超时被杀时 `finally` 不执行，锁留 2 小时；3 次自动重启每 5 分钟一次，全部撞锁退出。

### 价格

- **匹配核心逻辑在 `scripts/`**（`match_catalog.py:42-93`）：`variant_signature` / `spec_ok` / `lang_ok` / `prefix_conflict` 是价格正确性的核心，却写在脚本里，没有测试；`pricing/overseas.py:41,63,175` 还并存一套语义不同的旧实现。
- **`price_runs.week` 语义混用**：`record_price_run` 写 `2026-W47`，新脚本写 `2026-11-18`。实测 1–8 行是 ISO 周，9–12 行是日期。
- **分类准确率约 63% 且已继承到 550 个新品**：342 个「涂料」里 41 个是套装/卡牌/模型；导入脚本另有一套 `BOOK_HINT`/`PAINT_HINT`，品类规则散落两处。
- **涨跌功能未经验证**：只有 11-18 / 11-19 两次观测且价格完全相同，`price_movements` 唯一输出是闲鱼那条 +117.2%（不同卖家集合造成的假涨跌）。

### 工程

- **项目不是 git 仓库**（实测无 `.git`）：无法回滚、无法 diff，本轮 500+ 行改动只靠文档和一份手工备份。
- **`scripts/` 无测试**：365 个用例全部覆盖 `src/`，最新的匹配/导入/周更逻辑零测试。
- **`doctor` 缺关键项**：磁盘、alert、在途状态、上次成功推送、cookie 登录态、上次推送链接可达性都不查。

## 四、架构判断

分层大体是对的：`adapters/ → content → pipeline → runner → render/notify`，`pricing/` 独立，`db.py` 统一收口。三个问题：

1. **领域逻辑溢出到脚本**。价格匹配、新品导入、周更编排都是核心业务，却写在 `scripts/` 里，导致「无测试 + 无法复用 + 两套实现并存」。这不是风格问题，是价格正确性没有测试保护。
2. **状态机不完整**。推送台账有 0/1/2 三态，但没有「发送中→已确认」的恢复路径；`runs.status` 恒为 `ok`，失败不可见。
3. **可观测性停在「跑完了没」**。日志记录成功数量，不记录失败原因；正文失败率、跨源重复率、预算超支都没有指标。
