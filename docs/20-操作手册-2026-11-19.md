## 一、系统全景

```
                    ┌── 定时任务 InfoTwitter-Daily（每天 12:00）
                    ↓
采集 46 源 → LLM 分析 → 聚类/评分 → 选槽 → 排版 → 推送(PushPlus) + 日报页(8080) + 台账
```

## 二、日常运行

### 2.1 自动（正常情况下什么都不用做）

```
每天 12:00  InfoTwitter-Daily  → run.py run
```

检查运行结果：

```powershell
.\.venv\Scripts\python.exe run.py status      # 今日台账 + 状态
.\.venv\Scripts\python.exe run.py doctor      # 9 项自检
```

`doctor` 全 OK 就说明配置、代理、密钥、库、任务都正常。**唯一的 WARN 是"推送有效性未验证"，属正常**
（`--probe-push` 会真发一条，平时别开）。

### 2.2 手动跑

```powershell
# 完整跑（同定时任务）
.\.venv\Scripts\python.exe run.py run

# 不采集，用库里现有数据重算（改评分/排版后验证）
.\.venv\Scripts\python.exe run.py run --no-collect

# 只预览不推送、不写台账
.\.venv\Scripts\python.exe run.py run --no-collect --dry-run

# 只跑采集
.\.venv\Scripts\python.exe run.py collect

# 已推送过的一天要重发（会先渲染到 _dryrun，发送成功才覆盖站点）
.\.venv\Scripts\python.exe run.py run --force
```

**注意**：同一天重复跑会走 `already_pushed` 短路（不重复推送、不覆盖已发布日报）。
`--force` 才会重发，且失败时不动站点根。

### 2.3 每天的检查点（30 秒）

```powershell
run.py doctor                       # 全 OK
run.py status                       # 今日 6 个槽都有记录
run.py sources                      # 各源产出，失败列应为 0
```

## 三、价格数据链路（6 步，按顺序跑）

价格是**独立链路**，一天或一周跑一次即可，不阻塞日更。

### 步骤 1：翻译商品名（只在遇到新商品时跑）

```powershell
.\.venv\Scripts\python.exe scripts\translate_products.py                 # 全部缺中文名的
.\.venv\Scripts\python.exe scripts\translate_products.py --limit 50 --dry-run   # 先看效果
.\.venv\Scripts\python.exe scripts\translate_products.py --force --limit 100    # 重译
```

| 项 | 值 |
|---|---|
| 幂等 | 是，只处理 `name_zh` 为空的；`--force` 才重译 |
| 速度 | 1740 条约 1 分钟（20 条/批、4 并发） |
| 成本 | 约 17 万 token ≈ ¥0.3 |
| 留痕 | `products.name_zh_source` / `name_zh_at` + `name_translations` 历史表 |

### 步骤 2：抓海外目录（整站分类页）

```powershell
.\.venv\Scripts\python.exe scripts\crawl_overseas_catalog.py                # 全部 6 个入口
.\.venv\Scripts\python.exe scripts\crawl_overseas_catalog.py --limit-pages 5 # 先试 5 页
.\.venv\Scripts\python.exe scripts\crawl_overseas_catalog.py --only-landing warhammer-40k
```

| 项 | 值 |
|---|---|
| 产出 | `overseas_catalog`（url / 标题 / £价格 / 分类路径） |
| 规模 | 753 个分类页 → 5675 个商品 |
| 速度 | 约 6 秒/页，全量约 65 分钟 |
| 幂等 | 按 url upsert，可反复跑 |

抓完会自动写一条 `price_runs` 记录（`crawl_catalog`）。

### 步骤 3：补官方货号（匹配的关键）

```powershell
.\.venv\Scripts\python.exe scripts\fill_catalog_codes.py --limit 50   # 分批
.\.venv\Scripts\python.exe scripts\fill_catalog_codes.py              # 一直补到完
```

| 项 | 值 |
|---|---|
| 产出 | `overseas_catalog.product_code`（GW 数字码或第三方字母码） |
| 规模 | 4058 / 5675 条有码 |
| 速度 | 约 1.8 秒/条，4000 条约 2 小时 |
| 幂等 | 只处理没码的；已抓过详情的直接复用，不重复请求 |

**为什么值得花 2 小时**：货号能对上就是 100% 确定的匹配，比名字可靠得多。

### 步骤 3.5：把目录里的书补进主表（只在新书出现时跑）

```powershell
.\.venv\Scripts\python.exe scripts\import_catalog_books.py --dry-run   # 先看要补哪些
.\.venv\Scripts\python.exe scripts\import_catalog_books.py
.\.venv\Scripts\python.exe scripts\translate_products.py               # 新商品还没有中文名
```

| 项 | 值 |
|---|---|
| 做什么 | 把「有 GW 官方码、主表没有、标题像小说/规则书」的 SKU 补进 `products` |
| id 规则 | 直接用官方码（如 `60040181478`），并写进 `product_codes` |
| 过滤 | 必须命中 `PB/HB/paperback/hardback/novel/omnibus/black library`，且不含 `codex/cards/dice/miniatures` 等 |
| 幂等 | 是，已存在的码会跳过 |

**为什么需要这一步**：主表来自 GW 中国调价表，那张表**一本小说都没有**；
不补进来，Black Library 的书永远进不了价格体系。

### 步骤 4：抓商品详情（可选，慢）

```powershell
.\.venv\Scripts\python.exe scripts\crawl_product_details.py --limit 50
.\.venv\Scripts\python.exe scripts\crawl_product_details.py            # 所有已匹配的
```

产出 `product_details`：描述（775–1188 字）、件数（"73 components"）、库存状态、货号。

### 步骤 5：匹配 + 写价格点

```powershell
.\.venv\Scripts\python.exe scripts\match_catalog.py --dry-run          # 先看匹配结果
.\.venv\Scripts\python.exe scripts\match_catalog.py                    # 只回填匹配关系
.\.venv\Scripts\python.exe scripts\match_catalog.py --write-points     # 同时写 gw_uk 价格点
```

| 项 | 值 |
|---|---|
| 两层匹配 | ① GW 货号精确匹配（权威）② 名称 + 变体签名（≥0.9） |
| 守卫 | 货号不一致直接拒；`pack/ml/season/issue` 必须一致；语言仅在双方都有标记时比对 |
| 门槛 | 价格必须 > 0（目录里 380 条 £0 的预售价会被跳过） |
| 速度 | 秒级 |
| 幂等 | 是（先清 `product_id` 再重算，价格点按 `(product, channel, platform, date)` upsert） |

## 四、常用查询

### CLI

```powershell
run.py price --limit 5                 # 看价格摘要（5 行）
run.py price --line 40k --limit 10     # 只看 40k 产品线
run.py sources                         # 按源产出统计
run.py history --days 7                # 推送历史
run.py replay --top 10                 # 零成本重算排名（调权重用）
```

### SQL（sqlite3 或任意客户端）

```sql
-- 价格覆盖
SELECT channel, COUNT(*) n, COUNT(DISTINCT product_id) p
FROM price_points GROUP BY channel;

-- 某商品的全部价格
SELECT channel, platform, price, currency, price_cny, observed_at, confidence
FROM price_points WHERE product_id='01-13' ORDER BY observed_at DESC;

-- 海外目录匹配情况
SELECT COUNT(*) total,
       SUM(product_id IS NOT NULL) matched,
       SUM(length(coalesce(product_code,''))>0) with_code
FROM overseas_catalog;

-- 没匹配上的商品（按品类）
SELECT category, COUNT(*) FROM products p
WHERE NOT EXISTS (SELECT 1 FROM price_points pp
                  WHERE pp.product_id=p.id AND pp.channel='gw_uk')
GROUP BY category ORDER BY 2 DESC;
```

## 五、故障处理

### 5.1 运行锁被占用

日志出现 `运行锁被占用`，CLI 返回 **4**（这是刻意的：任务计划能看见失败）。

```powershell
Get-Content data\.run.lock        # 看是谁的 pid
Remove-Item data\.run.lock        # 确认没进程在跑后手动删
```

锁超过 2 小时会自动判定为遗留并清理。

### 5.2 代理挂了

海外源（WHC / Reddit / gnews / Element）会整批失败，国内源正常。

```powershell
run.py doctor                     # 看"网络 / 代理"是否 FAIL
```

代理恢复后重跑即可；已采集的数据不会丢。

### 5.3 某个源持续失败

```powershell
run.py sources                    # 看哪个源 fail 高
```

连续失败的源在 `config/sources.yaml` 里设 `active: false` 停掉（Reddit 的 5 个源就是这么处理的）。

### 5.4 推送没收到

```powershell
run.py status                     # 台账有没有记录
Get-Content logs\alert.log -Tail 20   # 有没有告警
```

台账有记录且 `delivery_ok=1` 说明发出去了，问题在通道侧。

### 5.5 价格看起来不对

```powershell
run.py price --limit 5            # 先看展示
```

再查该商品的 `price_points`：`confidence` 为 `low` 的不参与最低价；
`note` 里写了匹配到的原始标题，可以核对是不是同一件商品。
