## 1. 一句话总结

三个"每天都会发生"的 P0 已经不再发生：**推送里的链接能打开了、通知标题是中文标题而不是 HTML 源码、可信度徽章不再因为同一篇内容被重复收录而虚高**。此外把"LLM 编造事实"从提示词约束变成了程序校验（`claims` 表从 0 行变成 279 行，每条 evidence 都能在原文里定位）。

## 2. 用户可感知的变化

收到明天 12:00 那条推送时，会和之前不一样的地方：

| 位置 | 之前 | 现在 |
|---|---|---|
| 微信通知标题 | `<div style="font-size:15px;...` | `【战锤日报 11-18】` |
| 每条摘要 | 被截到 60 字，末尾一律「…」 | PushPlus 通道给到 120 字，只有企微 2048 字节才压到 60 |
| 每条信息 | 只有标题+摘要+分数 | 多了「💡 为什么重要」，事件类型显示中文（规则/模型新品/电子游戏…） |

| 日报页 | 纯静态，无反馈入口 | 每条下面有 5 个按钮（👍👎🚫🔁🛒），点一下真的会写库并影响次日排序 |

## 4. 数据库迁移

新增列全部通过 `Database._migrate()` 幂等补齐（`PRAGMA table_info` 判断后 `ALTER TABLE`），**已在本机生产库实跑成功**：

```
迁移：raw_docs 新增列 discovered_at / derived_tier / publisher_domain / time_source
迁移：sources  新增列 fake_reports
迁移：stories  新增列 published_at
回填：raw_docs.discovered_at = COALESCE(discovered_at, fetched_at)   （203 行）
新建索引：idx_raw_discovered（放在 ALTER 之后，否则旧库会直接报错）
```

新表：`feedback_dedup(story_id, signal, day)`。

兼容性取舍：
- `story_id` 的种子仍是「最早那篇的标题 + 原文发布日期」，**没有改成入库时间**——否则迁移当天所有 story id 都会变，已推送的内容会被重推一次。`first_seen_at` 单独改为入库时间，两者解耦。
- 迁移连续执行两次无副作用（已验证）。

## 8. 下一步建议

1. **先观察 3 天真实推送**再继续改。这轮改动里有两处会影响选槽结果（多源计数、多样性不再回填），需要真实数据确认日报没有变短。
2. 如果发现条数变少，**不要立刻加回回填**，先看 `diversify` 的判定阈值（`jaccard_min=0.18` 偏松）——那是设计 §17.4 定的，改它要有数据支撑。
3. 下一轮优先做**中文源可用性排查**，它直接决定槽 6 是不是只有 B 站。
4. `git init` 建议尽快做（`.gitignore` 已就绪），否则下次大改还是没有可对比的历史。
5. 日报服务目前跑的还是**旧代码**（整改前启动的进程）。新代码的安全项（按天令牌、关目录列表）要等进程重启后才生效；下次 12:00 的定时任务不会重启它，建议手动重启一次。
