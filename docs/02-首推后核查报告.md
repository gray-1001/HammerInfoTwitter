## 三、问题清单

### P1-1　锁冲突被记成「今日日报推送失败」

**证据**：`logs/alert.log`

```
2026-11-18T12:55:45  今日日报推送失败：运行锁被占用，本次未执行：…（0 秒）
```

而当天 12:04:51 的推送是**成功**的（6 条全部 `delivery_ok=1`）。

**根因**：`runner._write_alert()` 无条件给所有告警加前缀「今日日报推送失败：」：

```python
fh.write(f"{now_iso()}\t{today}\t今日日报推送失败：{reason}\n")
```

**影响**：运维看到这行会以为当天推送失败，实际成功。告警系统的可信度被自毁。

**建议**：告警文案由调用方决定（`_write_alert(cfg, today, reason, kind="push"|"lock"|"run")`），锁冲突与运行失败分开记。

### P1-2　首推当天有 2 个额外进程抢锁

**证据**：12:00 日志中两行，但主流程未中断

```
12:00:14 ERROR 已有另一个运行实例在进行，本次退出：运行锁被占用（12 秒）
12:00:17 ERROR 已有另一个运行实例在进行，本次退出：运行锁被占用（15 秒）
```

`runs` 表显示 12:00 只有 #103 一个实例，说明这两个进程在写 run 记录前就退出了 —— **锁正确阻止了重复运行**，但来源不明：

- 计划任务只有一个动作、一个触发器（已核实）
- 任务计划程序操作日志未启用，无法追溯
- 全库无代码会 spawn `run.py run`（`ensure_running` 只拉起 `serve`）

**最可能**：计划任务 `StartWhenAvailable=True`，把 11-17 12:00 那次「任务创建前已错过」的触发补跑了。

**影响**：当前无害（锁生效），但会在 `alert.log` 制造假告警（见 P1-1），且长期存在「不知道谁在跑」的隐患。

**建议**：开启 TaskScheduler 操作日志；锁冲突告警降级为 warning；补跑场景在日志里标明「补跑」。

### P1-3　一个僵尸 `serve` 进程

**证据**：

```
PID 106712  pythonw  内存 5MB   启动 11-17 21:08   监听：无
PID 78212   pythonw  内存 20MB  启动 11-17 21:08   监听：0.0.0.0:8080
```

两个 `serve` 在同一秒启动（启动项 vbs + `ensure_running` 自愈竞争），一个绑定成功，另一个未绑定任何端口但常驻不退。

**影响**：浪费一个进程；`ensure_running` 的 `port_open` 探测存在竞态窗口，理论上可能反复拉起。

**建议**：`ensure_running` 探测前先等待/重试几次；服务启动失败应显式退出而不是静默挂起。

**建议**：改完代码后至少跑一次 `--dry-run --force` 走完排版，确认渲染无误。

### P1-5　价格数据两天没有更新，日更链路不抓价

**证据**：槽 5 显示「暂无变动 · 数据日 2026-11-18」，但 `price_points` 仍是 3,509 条，`gw_uk` 14 条，`xianyu` 3 条 —— 与昨天完全一致。

`auto_refresh` 只做「人工 CSV 有更新就导入」，不触发 Element Games / 闲鱼抓取。

**影响**：「模型价格速览」每天内容不变，等于静态表；用户看到的「暂无变动」其实是「没去抓」。

**建议**：日更里对 `preorder/new` 状态的少量 SKU（≤10）做海外价刷新（无需 LLM，约 40 秒）；或者明确在槽 5 标注「价格每 N 天更新一次」。

4. **源健康只有记录没有动作**（P1-6）：`fail_count` 在涨，但没人根据它做决策。
5. **代码演进快于验证**（P1-4）：首推后 3 个核心文件被改，未走完整路径验证。
