## 2. 四块工作

### 2.1 选槽质量

**破平规则（§7.2）**：`tie_break_key()` 四段键——总分、量级、权威、首发时间。
之前只按总分排，同分时依赖 Python 稳定排序的输入顺序，导致同一批数据跑两次可能得到不同结果，调参也无法对比。

**中文社区卡（§7.3）**：按设计给的五个维度独立打分（30/25/20/15/10），权重走配置。
关键判断：
- 影响面：中文相关词命中数（中文/引进/汉化/国内/B站/贴吧…）
- 可获得性：能不能真买到/参加（预售/开订/淘宝/闲鱼/门店/展会/直播…）
- 来源可信：官方中文 > 机核/游研社 > B站 UP > 中文聚合
- 稀缺性：来源是否全为中文源 + 来源数量（无法跨语言比对，用代理指标并写进注释）
- 时效：复用通识卡的时效函数

**常青惩罚**：涂装/教程/评测/战报/梗图/meme/整活 等乘 0.65，并要求量级 ≥ 2。

实测效果（真实数据）：

```
通识分 34–51 的 12 条中文候选 → 中文社区卡 47–85 分
「懿躅涂装分享：NMM 基里曼新手从零学涂装」78.0 → 50.7（被 60 分线挡掉）
槽 6 从「猫 meme」变为「战锤30K视频：HH3.0 吞世者上桌模型展示」
```

**商品判定（§9.1）**：从 `event_type == mini` 放宽到「事件类型 + 强商品词」，并排除涂装/评测/战报。
设计里 SKU 范围是 boxed/codex/mini/book/paint，只认 mini 会漏掉圣典、小说、涂装类新品。

**槽 5 差分（§9.2 / §10.3）**：新增 `price_movements()` 算窗口内涨跌；
槽 5 显示涨跌幅，无变动时表头标「暂无变动」，数据超 7 天未更新会显式警告。

### 2.2 可信度闭环

**claim 跨文档交叉印证（§6.3）**：这是设计里最核心但一直没落地的能力。

实现：把同一 story 下**每个文档**的 claim 收集起来，按「去数字骨架 + 词集合 Jaccard ≥ 0.5」归并，
统计支持它的**独立域名**数量；≥2 个域名且其中至少一个 L0/L1 才标 `promoted`。

**中文 claim 的坑**：`token_set()` 按空白切词，中文整句会变成一个 token，导致中英混排时永远匹配不上。
新增 `claim_tokens()`：CJK 用二元字符组，拉丁用词。

**矛盾检测**：同一主张骨架下出现不同的价格/日期数字 → `contradict=1`，story 降一级并加注。

**如实说明**：这套机制在合成数据上验证通过（同域不升级、L3 互证不升级、£35 vs £40 能检出），
但**当前生产数据里只有 3 个 story 有 ≥2 个独立域名，所以实际 `support_count ≥ 2` 为 0 条**。
这不是实现问题，是源覆盖不足——中文源和英文源都上来之后才会真正发生。

**confidence 文案**：把 `L0/L1/L2/L3` 翻译成人话，并区分「多源印证」与「权威报道」、「单一来源」与「社区多源」。
矛盾时直接显示「主张存在矛盾」。

**quote_zh**：LLM prompt 增加该字段，随 quote_en 一起落库，报告页引文下方显示中译。

### 2.3 中文源：实测推翻了上一轮的判断

上一轮结论是「13 个源长期零产出」。这一轮实际探测后发现：

| 源 | 实测结果 | 上一轮判断 |
|---|---|---|
| 中文 Google News（战锤40K） | **HTTP 200，35 条真实中文战锤新闻** | ❌ 误判为"零产出无告警" |
| 中文 Google News（战锤 模型） | **HTTP 200，18 条** | ❌ 同上 |
| 机核 gcores | HTTP 200，20 条，但 7 天内无战锤条目 | ✅ 判断正确（关键词过滤） |
| 游研社 yystv | HTTP 200，12 条，同上 | ✅ 判断正确 |
| RSSHub（贴吧/微博） | **HTTP 403 + Cloudflare 挑战页** | 未验证 |

真正的原因不是源坏了，而是**三道窗口**（采集 96h / 分析 96h / 聚类 48h）把内容全挡在外面——
中文战锤新闻最新一条在 **122 小时前**。

修正：
1. 4 个中文源 `collect_hours` → 168h；
2. 分析/聚类窗口改为 `max_collect_hours`（跟随最宽的源，不再硬编码 96）；
3. 槽 6 单独给 `cn_slot_days: 7` 的候选窗口；
4. **同时收紧通识槽**：`published_at` 超出采集窗口的新闻不得进槽 1–4——否则"放宽采集"会变成"推旧闻"。

结果：中文源 0 → 8 条入库；槽 6 候选 25 → 46 条（2 条来自中文 Google News）；槽 6 标注「N 天前」。

**RSSHub 的结论**：公共实例 rsshub.app 被 Cloudflare 挡在 403，需要自建实例才能接贴吧/微博。
这条现在有据可查，不再是"未接入"的模糊说法。

### 2.4 稳健性

- **正文抓取重试**：外链抓取 2 次 + 退避（之前 0 次重试，一次抖动就永久丢这篇正文）。
- **代理例外**：解析 Windows `ProxyOverride`（localhost / 127.* / 192.168.* / `*.local` 等），
  命中项改用直连 client。httpx 的 client 级 proxy 无法按主机切换，所以额外维护一个直连 client。
- **价格自动刷新**：日更任务检查人工快照 CSV 的 mtime，有更新就自动导入并记 `price_runs`。
  GW 调价表与海外价仍需外部动作（拿到新表 / 人工确认匹配），**不假装自动化**。
- **doctor 遗留表提示**：`skus` / `price_snapshots` 是设计 §4 的原案，已由 `products` / `price_points` 取代。

## 4. 剩余缺口（明确不做或做不了）

| 项 | 状态 | 原因 |
|---|---|---|
| 淘宝客 API | 不做 | 需要实名账号 + 应用审核 |
| 闲鱼采集 | 不做 | 登录态 + 风控，合规优先 |
| 贴吧 / 微博 | 阻塞 | RSSHub 公共实例被 Cloudflare 拦截，需自建 |
| embedding 聚类 | 推迟 | P2；当前三路判定在真实数据上正常 |
| 海外价周更自动化 | 推迟 | 自动匹配容易把错配写进库，需人工确认 |
| B 站内容质量 | 未解决 | 中文源里 B 站占比过高，这是源结构问题，不是打分问题 |
| 语义级 claim 对齐 | 部分 | 当前靠 Jaccard 0.5，同义改写仍会漏；等有多域名数据后再评估是否值得上 embedding |

## 5. 下一步建议

1. **先跑 3–5 天真实推送**，重点看两件事：槽 6 是否还会选出低价值内容、通用槽有没有因为"发布窗口收紧"而变少。
2. 如果槽 6 仍然被 B 站霸占，下一步应该**补源**（自建 RSSHub 接贴吧、或接机核的战锤标签页），而不是继续调权重。
3. `claims.support_count ≥ 2` 一直是 0，说明交叉印证缺"料"。等中文+英文双源都稳定后，可以顺手把矛盾检测的阈值调紧再看。
4. 价格模块的自动采集只做到"CSV 有更新就导入"。真要自动，得先解决"怎么拿到新调价表"——这属于外部流程。
