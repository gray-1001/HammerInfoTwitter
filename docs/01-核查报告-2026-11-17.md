## 3. 架构核查

### 3.1 设计的分层 vs 实际的分层

设计 §3 定义了 8 层：采集 → 归一化 → 聚类 → 校验 → 排序 → 呈现 → 推送 → 反馈。实际实现：

| 设计层 | 实际模块 | 状态 | 评价 |
|---|---|---|---|
| 采集 | `adapters/` + `httpclient.py` + `content.py` | ✅ 存在 | 分层清晰，4 个适配器 + 统一的 Fetcher，是全项目质量最高的部分 |
| 归一化 | 无独立层 | ⚠️ 缺失 | 语言识别靠 `source.lang` 静态配置；清洗散落在各适配器的 `clean_text`；翻译直接塞进 LLM 抽取 |
| 聚类 | `pipeline.cluster_docs` | ✅ 存在 | UnionFind + 三路判定（实体重叠 / Jaccard / 包含度），思路正确 |
| 校验 | `pipeline._build_story` 内 4 行 | ❌ 名存实亡 | 只做"取最高 tier + 数 source_id"，claim 级校验完全没有 |
| 排序 | `pipeline.score_story` + `select_slots` | ✅ 存在 | 评分与选槽分离，可回放，设计兑现度最高 |
| 呈现 | `render.py` | ⚠️ 有耦合 | 排版层直接消费 `slots` 这个半结构化 dict，字段靠约定而非契约 |
| 推送 | `notify.py` | ✅ 存在 | 通道抽象正确（`Notifier` + `content_type` + `max_bytes`），但标题契约缺失 |
| 反馈 | `server.py` | ⚠️ 断链 | 后端完整，前端不存在 |

### 3.2 六个架构性问题

**A-1「校验层」被压缩成了两行代码，这是本次核查发现的最根本的架构退化。**
设计 §6 给了 claim 抽取、交叉印证、矛盾检测三件事，落地时只保留了"最高 tier + 多源计数"。表面上省事，实际上把整个"可信"卖点换成了一个**会被重复采集轻易骗过**的计数。数据实证：33 条虚假 L1。

**A-2 采集层的"源"承担了它不该承担的语义，导致新鲜度与可信度双重失真。**
`tier` 写在 `sources` 表（源级），但 Google News 聚合条目里每条的真实发布域名不同，代码算了 `derived_tier` 却丢弃（BUG-06）；`published_at` 在 browser 源里直接用抓取时刻（BUG-10）；`source_id` 被当作"独立信源"（BUG-03）。**"源"这个概念同时承载了订阅渠道、可信层级、独立性判定三个不同语义**，这是多个缺陷的共同根因。

**A-3 两套价格数据模型并存，schema 已经分裂。**
`schema.sql` 里 `skus` + `price_snapshots` + `price_runs`（设计 §4 的原案，全部 0 行）与后来新增的 `products` + `price_points`（3,495 行）同时存在。`doctor` 还在统计 legacy 的 `skus`。这是典型的"新功能上线但旧模型没退役"。

**A-4 价格模块与主流水线是两条互不相连的轨道。**
`run_daily` 对价格只做一次读（`build_slot5_rows`），采集/导入全在 CLI 里。设计 §9.2 说的"每天抓一次"在架构上就没有落点。槽 5 因此冻结在 11-17 的快照上。

**A-5 幂等被实现了两次，两次都不完整。**
SQL 层有 `UNIQUE(push_date, slot)`，Python 层又写了一遍 `already_pushed_slot(today, 1)`。结果是：约束只在写入时覆盖，判断只在槽 1 生效，`--force` 还会把历史记录覆盖掉。**幂等这类性质应该只有一处实现**。

**A-6 可观测性只做了"打印"，没做"判定"。**
`doctor` 有九项检查，但退出码只看前 5 项；`sources.fail_count` 被"空结果=成功"清零；`Fetcher.stats()` 定义了却从未被调用（熔断域名不可见）。项目有可观测性的形，没有可观测性的用。

## 4. P0 缺陷详述

### BUG-01 · 推送里的「完整版」链接恒定 404

**【实测】**

```
GET http://192.168.1.100:8080/reports/2026-11-17.html  →  404
GET http://127.0.0.1:8080/reports/2026-11-17.html      →  404
GET http://127.0.0.1:8080/2026-11-17.html              →  200（14159 字节）
GET http://127.0.0.1:8080/latest.html                  →  200（14159 字节）
```

**位置**：`runner.py:154` 与 `server.py:178`

```python
# runner.py:154
report_url = f"{cfg.report_base_url()}/reports/{today}.html"

# server.py:178 —— 服务把 reports/ 当作站点根
handler = functools.partial(BoundHandler, directory=str(report_dir))
```

**根因**：URL 构造端与服务根目录端的约定不一致。文件在 `reports/` 里，但服务以 `reports/` 为根，所以 `/reports/x.html` 会被解析成 `reports/reports/x.html`。

**影响**：设计 §10.2 的"完整版页面"承担三件事——分项得分明细、可信度理由、反馈入口。现在这扇门是关的，而且因为 `ensure_running()` 会成功把端口拉起来，`doctor` 又只探测 `latest.html`，这个死链**永远不会被自检发现**。

**修复（二选一，推荐 A）**：

```python
# A. 改 URL（1 行，零风险）
report_url = f"{cfg.report_base_url()}/{today}.html"

# B. 改服务根目录（保留 /reports/ 语义，但要处理静态资源）
handler = functools.partial(BoundHandler, directory=str(report_dir.parent))
```

无论选哪个，都必须把「推送实际使用的那个 URL」纳入 `doctor` 的真实 HTTP 探测，否则同类回归还会再来。

### BUG-02 · 微信通知标题是一段 HTML 源码

**【实测】** `reports/push-2026-11-17.html` 全文 **4355 字符 / 5395 字节，只有 1 行**：

```
<div style="font-size:15px;line-height:1.7;color:#222"><b style="font-size:17px">战锤日报 · 11-17</b><span style="color:#999;font-size:12px">　正常</span></div>...
```

**位置**：`notify.py:95-98` + `render.py:247`

```python
# notify.py:95-98
lines = text.strip().splitlines()
title = lines[0].strip() if lines else "战锤日报"
if len(title) > 100:
    title = title[:99] + "…"
```

```python
# render.py:247 —— 整篇 HTML 无换行
html = "".join(parts)
```

**根因**：Notifier 假设"首行即标题"，这个假设只对纯文本版本成立。`content_type == "html"` 时首行是整篇 HTML。

**影响**：`config.yaml` 当前就是 `pushplus_template: html`，所以**每天都会发生**。用户通知栏显示 `<div style="font-size:15px;line-height:1.7;color:#222"><b ...`，真正的「战锤日报 · 11-17」被截断丢弃。

**修复**：把标题从"隐式约定"提升为"显式契约"。

```python
# render.py 新增
def build_push_title(slots: dict, date: str) -> str:
    return f"【战锤日报 {date[5:]}】"

# render.py
def build_push_message(...) -> tuple[str, str]:   # (title, body)
    ...

# notify.py
class Notifier:
    def send(self, title: str, text: str) -> tuple[bool, str]: ...
```

若暂时不想改签名，最小补丁：

```python
title = re.sub(r"<[^>]+>", "", lines[0])[:100] or "战锤日报"
```

```python
    # 仅 L2 可因多源印证升级；L3 不升级，防同源洗稿（见设计 §6.3）
    authenticity = "L1"
```

**根因**：设计 §6.3 要求「≥2 个**独立来源**（**不同域名**）」，代码用了 `source_id`——而 `source_id` 是"查询配置"的 ID，不是"发布者"的 ID。`bilibili_wh` / `bilibili_model` / `bilibili_40k` 抓的是同一个 B 站搜索 API，`gnews_40k` / `gnews_aos` 抓的是同一个 Google News。

**连带影响**：`buzz_score(n_sources) = 1 + 0.9 × (n-1)`，权重 20。同一个视频因 3 个源被算成 `buzz=2.8`（而非 1.0），凭空多拿 `20 × 1.8 / 5 = 7.2` 分——足以改变槽位排序。

**修复**：

```python
def _independent_sources(docs: list[dict]) -> set[str]:
    """独立来源 = 不同的发布域名；同一内容的重复收录不算。"""
    keys: set[str] = set()
    for d in docs:
        domain = (d.get("publisher_domain")
                  or urlparse(d.get("url") or "").netloc
                  or d["source_id"]).lower()
        domain = re.sub(r"^www\.", "", domain)
        keys.add(domain)
    return keys
```

同时 `_build_story` 里 `n_sources = len(_independent_sources(docs))`。

**测试也需要改**：`tests/test_pipeline.py:179-189` 的 `test_l2_upgrades_with_corroboration` 用 `source_id='a'` 与 `'b'` 断言 L1，这个用例**固化错误的语义**，应改为断言"同 URL 不升级"与"不同域名才升级"两条。

### 5.2 采集可靠性

#### BUG-08 · 熔断按"重试次数"计数、按域名共享、整轮不复活

```python
# httpclient.py:84-87
self._host_fails[host] = self._host_fails.get(host, 0) + 1
if self._host_fails[host] >= self.breaker_threshold and host not in self._dead_hosts:
    self._dead_hosts.add(host)
    log.error("域名 %s 连续失败，本次运行熔断", host)
```

四个问题叠加：

1. **计数单位是"尝试"不是"请求"**：`retries: 4` × `breaker_threshold: 3` 意味着**单次请求的第 3 次重试就把域名判死**，第 4 次重试纯属浪费。
2. **按 host 共享**：`news.google.com` 承载 15 个源、`www.youtube.com` 承载 11 个、`www.reddit.com` 承载 2 个 —— 合计 **28/38 个启用源**在同一条熔断线上。
3. **整轮不复活**：`_dead_hosts` 只在 `__init__` 里为空，从不清理。这与模块自己的 docstring「实测表现为成段故障后自行恢复」直接矛盾。
4. **不可见**：跳过只打 `log.debug`，INFO 日志里看不到"因熔断被跳过"。

**【实测】** 日志中 `news.google.com` 熔断 9 次、`www.reddit.com` 熔断 17 次。

**影响**：一次 3 连败就能让当天 2/3 的源静默消失，且失败源列表只记录"当次正在跑的那一个"。

**修复**：① 计数移到 `for` 循环外（每请求 +1）；② 熔断记录 `dead_since`，N 分钟后放行一次（半开），成功即复活；③ 跳过时 `log.warning` 并计入 `failed`；④ 采集前用 `doctor` 的轻量端点做一次代理预检。

推送里因此出现 `WARHAMMER 40000: STARTER SET (CHN) GBP 43.29 → ¥1950` 这种荒谬组合（真实 GW 新手包接近 £90+）。而 `40-05` 的 note 里代码**自己已经写明「溢价 4.9× 异常，疑似匹配错误」**，但 `build_summary` 读取时完全无视 `confidence`。

```python
# pricing.py:410-414
def _similarity(a, b):
    ta, tb = set(_norm(a).split()), set(_norm(b).split())
    return len(ta & tb) / min(len(ta), len(tb))    # 除以 min()：2 词命中 2 词 = 1.0
```

**【实测】** `_similarity("WARHAMMER 40000: ASTARTES SPACE MARINES ASSAULT INTERCESSORS", "Space Marines") = 1.0`。

**修复**：① 相似度改 Jaccard（交/并）；② 增加品类与语言版本一致性校验（`(CHINESE)` vs `(ENG)`、`paint` vs `mini` 必须一致）；③ `confidence='low'` 不进入 `overseas` 或渲染为 `GBP 43.29(?)`。

### 8.4 验收标准（可执行，不是形容词）

| # | 验收项 | 判定方式 |
|---|---|---|
| 1 | 推送里的链接可打开 | `curl -o /dev/null -w '%{http_code}' <push 里的 URL>` = `200` |
| 2 | 推送标题是文案 | 收到的微信通知标题匹配 `^【战锤日报 \d\d-\d\d】$` |
| 3 | 无虚假可信度徽章 | `SELECT COUNT(*) FROM stories WHERE authenticity_note LIKE '%多源印证%'` 中，`source_ids` 涉及同一 URL 的为 0 |
| 4 | claims 可验证 | `SELECT COUNT(*) FROM claims` > 0，且 100% 的 `evidence` 能在对应 `raw_docs` 中定位 |
| 5 | 合格新闻不丢 | "published>24h 且 fetched≤24h"的 story 中，分数 ≥ 门槛的必须全部进入 `pushes` 或显式记入"未入选原因" |
| 6 | 失败可见 | 断网跑一次：`doctor` 退出码 ≠ 0；`logs/` 出现告警行；Windows 任务显示失败 |
| 7 | 槽 5 可信 | 5 行的海外价 `confidence` 全部 ∈ {high, medium}；每行标注数据日期 |
| 8 | 反馈闭环 | 页面点击按钮 → `feedback` 表新增一行 → `interests` 对应键变化 |
| 9 | doctor 不再假绿灯 | 人为把 `report_url` 改回 `/reports/`，`doctor` 必须报 FAIL |
| 10 | 干净机器可跑 | 新目录按 README 安装后 `python run.py doctor` 全部通过 |

### 8.5 不建议做的事（避免过度设计）

1. **不要现在做 embedding 聚类。** 现有三路判定（实体重叠 / Jaccard / 包含度）在 123 条真实数据上表现正常，聚类不是当前瓶颈——虚假可信度才是。
2. **不要为多 domain pack 提前抽象。** 设计 D7 自己也说了"不为多领域过度设计"。现在 `sources.domain` 恒为 `warhammer`，等真的有第二个领域再抽。
3. **不要在修 BUG-03 之前提高 LLM 使用量。** 输入污染不修，模型越好、错得越一致。
4. **不要删除 §8.4 的五级降级阶梯。** 它是这个项目写得最好的部分之一，问题只在 `diversify` 的回填破坏了"如实少推"，改那 9 行即可。
